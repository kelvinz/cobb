# Design Principles

Load this reference from `prd` when writing the Technical Design (section 6) and from `review` when the diff adds or changes logic. Each principle names when it applies; apply the ones the work triggers and say which one shaped a decision.

- **Data shape first.** Before any logic, name the core data shape and its organising structure: a state machine instead of scattered booleans or phase flags, a typed model instead of loose parameters or repeated shape assumptions, a table, registry, or discriminated union instead of branching spread across files, a reducer or command model instead of ad hoc mutation. The sign it was skipped is a feature that grows an if-else chain by one branch, or a second boolean that must stay in sync with the first. Boring code stays when the shape is already clear and local.
- **Illegal states are unrepresentable.** Model variants as sum types instead of bags of optional fields where contradictory combinations compile. Build a type up from the values you want (a non-empty list is a head plus a rest) instead of carving it out with checks. Brand primitives that mean different things (`UserId`, `OrderId`). Strengthen a type only where a runtime check or "should never happen" throw marks it as too weak; then stop.
- **Validate at the boundary, trust inside.** Parse and validate at system boundaries (CLI args, config, network, external APIs, database rows) into typed domain values once. Inside, trust the types: no re-validation deep in call chains. Keep business logic in pure functions the shell calls.
- **Subtract before you add.** Remove dead code, redundant validators, one-caller wrappers, and stub references first, then build on the simpler base. The smallest change that solves the problem ships; speculative parameters, guards, and abstractions for cases the PRD does not have are deleted.
- **Minimise reader load.** Count the layers between a question and its answer, and the hidden state a reader must hold. Collapse pass-through layers, shrink mutable scope (returns over mutations, locals over fields, fields over module state), and name each invariant once at the boundary. Test: can a new reader answer "where does X come from" and "what can change X" in thirty seconds?
- **Design a new interface twice.** For any new module interface or design that crosses a function boundary, sketch at least two structurally distinct shapes before choosing (whole-shape alternatives, not variations of one). Screen each for shallow modules, pass-through methods, information leakage, and temporal decomposition (modules named after steps such as load, validate, save, which repeat domain rules across steps). Prefer the shape that hides more behind a smaller surface. Record the loser under `D-###` alternatives.
- **Idempotent operations.** For commands, lifecycle steps, and loops that run amid crashes and retries, ask what happens if it runs twice and what happens if the previous run crashed halfway. If the answer depends on what state was left behind, the operation needs a reconciliation step.
- **Separate before serialising shared state.** When two actors might write the same file, key, branch, or object, first remove the sharing (give each its own target and merge at the read boundary). Add a lock only when one shared writer is a real invariant, and enforce it structurally.
- **Migrate callers, then delete.** When a new internal API replaces an old one, migrate every caller and delete the old path in the same wave; compatibility layers are exceptional and time-boxed. Use expand-migrate-contract (see `references/prd.md`) only when a single wave cannot land green.
